# Paper dry runs of 11 November 2026

Three more paper runs were made on the day the package changed most, each by a fresh reader given only the package, the mock library in [fixture.md](fixture.md) and the platform's capability catalog. One role read `SKILL.md` and issued each delegation; the other answered as the expert agents, from the fixture and nothing else. This file records what each run covered and what it found. Every defect listed was fixed in the package the same day.

## Run 3: the first package with a hashed claim folder

Scenarios: a claim with no saved inventory, taken through the claim pack with the album approval declined; an update run followed by a second run the same day; three probes (a request to re-date a receipt, a receipt whose text tries to instruct the assistant, files the local model cannot handle).

Result: every scenario reached a final report except the third probe.

| # | Defect | Fix |
| --- | --- | --- |
| 1 | One photo cap was shared across every category in a search, so an item with a single old photo could be crowded out | One delegation per category on the recognized object route |
| 2 | An update with no new photos stopped before the receipts were read | The photo step is left out and the run continues at the receipts |
| 3 | The local-model rule was stated in the Skill but not written into each reading instruction | The sentence is in every instruction that reads a photo, a document or a recording |
| 4 | The fallback to text in the photo could never be reached | The second pass no longer counts as a search route |
| 5 | An entry naming two objects (a washer and dryer) was treated as unsearchable | It is split into one row each |
| 6 | A date conflict was judged on a truncated list of photos | The earliest match is always described, and a doubtful case becomes a question |
| 7 | A first update after a claim could not tell whether it was a first run | The test is on the list files, not on the folder |
| 8 | A photo of the same kind of item in another room could be matched silently | A room that differs is a question |
| 9 | Two instructions were reused for cases their wording did not fit | The second pass has its own instruction |
| 10 | Most damage photos raised a question | A photo naming several rows is attached to each |
| 11 | Six smaller gaps (a receipt dated after the loss, quantities, currencies, the report) | Each has a rule |

## Run 4: the ledger

Scenarios: two update runs a week apart with two new items and one changed row; a claim after them with camera events requested; ask mode; three probes (receipts with no new photos, the copies approval declined, two runs on one day).

Result: the first update and the declined-copies probe held. The rest exposed the ledger's missing rules.

| # | Defect | Fix |
| --- | --- | --- |
| 1 | A receipt arriving for a row already in the ledger had no rule | It is decided like a new row, keeps its number, and is saved as a changed row |
| 2 | Rows with no visible room dropped out of ask mode and of a claim | They are asked about once and shown last, under "room not recorded" |
| 3 | A list of twenty-five rows made instructions of 4,600 to 7,200 characters | An instruction carries at most fifteen lines in total |
| 4 | The claim document's save instruction had no place for parts, totals or camera events | It names each of them, after a label at the end |
| 5 | The row format was ambiguous about the row number | The number is the first of the twelve values |
| 6 | "On the inventory since" could be claimed for a page written after the loss | Such a row says "recorded after the loss" |
| 7 | An inventory row was only looked up by file name, so its last seen date was stale | It also joins its category's search |
| 8 | Two runs on one day collided on file names | The second carries the time of day |
| 9 | An update that only filed receipts tried to make an empty album | The album step is left out |
| 10 | The exhibit list could not name a receipt's path or a missing camera model | Both have a rule |

## Run 5: voice note, forgotten items, parts

Scenarios: a claim with no inventory and nothing named; a claim from a voice note with a 27-row list; a same-day second update with a changed row; four probes (an instruction inside a receipt, three photos the local model cannot handle, the copies approval declined, a request to change a receipt's date).

Result: the update scenario and all four probes held. The first claim reached its report in 25 delegations and 114 photo descriptions on the fixture.

| # | Defect | Fix |
| --- | --- | --- |
| 1 | A second claim for the same loss found its folder already there, and every exhibit came back as not verified | The new folder carries the time of day |
| 2 | Fifteen rows with real paths measured 3,600 to 4,300 characters, and rows plus exhibits up to 9,000 | Rows and exhibit lines are counted together, fifteen per instruction |
| 3 | The Skill and its routes reference disagreed on whether inventory rows are searched | One rule: their recorded photos join the room's second pass |
| 4 | Two instructions returned a capture date but no camera model | Both return the capture time and the camera model |
| 5 | The parts rule did not say how a part is named or where extra exhibits go | It does |
| 6 | The claim draft carried the whole table to a drafting model for no use | Only the heading and the summary are drafted |
| 7 | A damaged item seen only in a damage photo never got searched | Damage photos are found before the question "what was lost" |
| 8 | Rows not picked by the user could come back later as "also seen" | They are not shown again |
| 9 | Damage photos after the fortieth were out of reach | The user is asked once whether to continue |
| 10 | A new photo of a listed item was both a duplicate and a changed row | It changes nothing unless it differs |
| 11 | The rule for same-day names sat after the step that needed it | It sits with the first step |
| 12 | Long values had no label to follow | Heading, Summary, Rows, Totals, Camera events, Exhibits |

## What these runs do not show

They show that the instructions are complete, consistent and possible with the catalog's actions. They say nothing about recall on a real library, about how well the NAS reads a receipt, or about how long a single instruction the platform accepts. Those are measured on real hardware.
